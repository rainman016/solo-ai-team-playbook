# 协作共用规范（岗位卡引用，需要时读）

- **验收标准写法**：每条都能判断通过或不通过；写明用什么数据、在哪里看；不写“体验良好”“合理”这类无法判断的词。
- **回报格式**：结论一句 → 版本（提交号或文件） → 已验证（附证据路径） → 未验证 → 失败项 → 待决定事项（每项标“简单拍板”或“需讨论”）。六项必须写在前 30 行；篇幅上限见项目 `文档上限.json`（说明见 `~/.claude/solo-ai-team-playbook/templates/doc-limits.md`）；返修、复核往后追加到同一份回报，不按轮次另建文件。
- **证据要求**：只给路径，不贴全文；所有证据对应同一版本；没亲自看过的写“未验证”。
- **接单与完成通知**：见通用规则“接单与通知”。
- **资源与换窗**：一窗一事，阶段做完先落盘。任务包外的新运行先给派你的总控发“【占用】资源｜预计多久｜是否独占”，按回复的时段启动，过了时段没启动就重新申请；跑完交退出证据（进程已结束、自己新建的临时资源已清理；任务包“约束”里要求保留的不动）。额度和上下文档位见 `CLAUDE-snippet.md`；换窗前给总控发“【换窗】窗口标题｜交接：路径”，由总控重派并更新任务池；到 90% 停下前发“【额度】窗口标题｜交接：路径”（子总控的发给项目总控）。同一项目在途的窗口放同一账号、同一权限模式，切号时一起切。
- **协商记录**（方案文件里的一节，总控对方案提了意见时写）：总控意见一句（附意见文件路径）｜本窗口意见一句｜合并后的改法｜未谈拢的点｜推荐。一轮＝总控交一次意见文件、本窗口回一次合并结果。最多 2 轮；第 2 轮仍有未谈拢的点，就在【待决定】里写“含 N 项分歧”，由 owner 在本窗口定。
- **找 owner 的方式**（子窗口这一侧）：
  - **怎么分**：看 owner 是否需要看材料、追问才能定。不需要的是简单拍板（选哪个、同不同意、施工中新增的费用、门禁授权），写进回报交总控；规则或方案的取舍清单（每项带推荐和理由、owner 只看清单就能定）也按简单拍板交总控，但产品方案确认整份不适用（按需讨论、不拆项），清单里的花钱项由总控通知子窗口单项发【待决定】。需要的是需讨论（需求、方案、原型、验收与手测，及随之提出的花钱），按下面的流程走。类别由子窗口在回报里标出，总控最终判定（小档手测交总控代呈）。
  - **请求**：发【待决定】通知，结论写“需 owner 到本窗口确认 N 项（含花钱 M 项；协商后改的 K 项；分歧 J 项；没有的写 0）”，然后等总控指引 owner 过来。
  - **确认**：
    - owner 来后，边看依据边定。不放一键拍板按钮。owner 说“全部按推荐”算逐项确认，也要逐项记下；涉及花钱或撤不回的项单独再确认一次。
    - 在方案或回报文件里写一节“owner 确认记录”，一项一行：项｜所选｜原话｜日期。
    - 按 owner 所选更新方案和验收标准；超出本次确认清单的变化只转总控、不改。
  - **收尾**：改回 `↳`，发【完成】通知“已确认 N 项｜记录：路径”。
  - **要 owner 手测、验收、拍板**：清单照 `templates/owner-checklist.md` 写，不概括；对话只放结论和要 owner 做的事，方法、数据放文件给路径。
